# 運用操作の画面化（案）

`CLAUDE.md` §10 と `docs/spec-v2.2.md` §4.1 に対する変更提案です。**承認されるまでは現行が正**で、この文書は提案の状態です。

- きっかけ: 「デプロイ後に `rails console` を開く運用は現実的でない」というオーナー指摘（2026-09-11）
- 対象: `/admin/users` を中心に、`rails console` でしか行えない操作の洗い出しと画面化
- 調べた範囲: `backend/config/routes.rb`、各コントローラの `permit`、`frontend/src/api/`、`db/schema.rb`

### 根拠

- `PATCH /api/users/me` が許可するのは `department` / `bio` / `pronouns` / `links` のみ（`api/users_controller.rb:79`）
- `/api/admin/users` は `index` / `create` / `destroy` と `suspension` だけ。**`update` が無い**（`routes.rb:33`）
- `PUT /api/events/:id` は `require_owner_or_admin` で owner と管理者の両方が通り、`tag_ids` も扱える（`api/events_controller.rb:7,48`）。**`frontend/src/api/` に呼び出す関数が無いだけ**
- `POST /api/projects/:id/participation` はあるが `DELETE` が無い（`routes.rb:13`）

### 画面が自分で宣言している

- `AdminUsersPage.tsx:247` —「パスワードの再発行と権限の変更は…`rails console` で対応します」
- `AdminPostsPage.tsx:256` —「企画の内容そのものは…`rails console` で対応します」
- `LoginPage.tsx:104` —「パスワードを忘れた場合も部長に連絡してください」

## 2. 決めてほしいこと

**どこまで画面にするか。** 3段階に分けました。上から順に、無いと運用が止まる度合いが高い順です。

| 段階 | 含むもの | 判断の性格 |
|---|---|---|
| **A** | 1 パスワード / 2 企画の編集 / 3 権限 | **これが無いと部員に配れない** |
| **B** | 4 年度 / 5 メール / 6 氏名 | Aと同じAPIに相乗りできる |
| **C** | 7 タグ管理 / 8 脱退 | 無くても回るが、そのうち詰まる |

**A と B をまとめて実装することを推します。** 4〜6 は `PATCH /api/admin/users/:id` という同じ入口で済み、別々にやると同じ画面を2回作ることになります。

いずれも `CLAUDE.md` §10「実装しないもの（提案も不要）」に載っている項目を覆すので、**§10 の書き換えが前提**になります。§10 と `.github/` は人間が自分で変える決まりです（`CLAUDE.md` §11-6）。

## 3. 各項目の仕様

### 3.1 パスワード（項目1）

**通知機能は作らない方針（`CLAUDE.md` §10）なので、メールでリセットリンクを送る方式は採れません。** 2本立てにします。

| API | 誰が | body | 備考 |
|---|---|---|---|
| `PATCH /api/users/me/password` | 本人 | `current_password`, `password` | 現在のパスワードを必ず検証する |
| `PUT /api/admin/users/:id/password` | 管理者 | `password` | 忘れた人が対象なので現在の値は求めない |

- `current_password` を必須にするのは、**端末を離席中に触られたときに乗っ取りを固定化させないため**。これが無いと、セッションを持っているだけの人がパスワードを書き換えられます
- 管理者が設定した値は**口頭で本人に伝えます**。「アカウントは部長が発行します」という既存の運用と同じ形です
- 長さ8文字以上の検証は既存の `User` バリデーションがそのまま効きます（`user.rb:36`）

> **⚠️ 既知の穴として記録します。** 現在のセッションは `session[:user_id]` しか持っていません（`sessions_controller.rb:31`）。
> **パスワードを変えても、他の端末で開いたままのセッションは生き続けます。**
> これを切るには `users` に `session_token` 列を足して cookie に載せる必要があり、§2（テーブル定義）に触ります。
> **今回のスコープ外**とし、別途判断してください。

### 3.2 企画の編集（項目2）

**APIは完成しています。フロントの画面を足すだけです。**

- `/events/:id/edit` と `/projects/:id/edit` を追加
- `CreatePage.tsx` のフォームを新規/編集の2モードで使い回す。編集では種別の切り替えタブを出さない
- 編集ボタンは詳細画面に置く。**出し分けは `owner.id === 自分` または `role === "admin"`**
  - `CLAUDE.md` §3-2 が禁じているのは「APIが返している情報をCSSで隠すこと」で、ボタンの表示はそれに当たりません。編集そのものは `require_owner_or_admin` がサーバー側で 403 を返して守ります
- `AdminPostsPage` の一覧からも各行の編集へ飛べるようにし、`rails console` の注記を消す

### 3.3 権限・年度・メール（項目3・4・5）

`PATCH /api/admin/users/:id` を1本足し、`role` / `enrollment_year` / `graduation_year` / `email` を受けます。

**ガード（すべてサーバー側で判定）**

- **自分自身の `role` は変えられない。** 誤って自分を降格し、管理者が0人になる事故を防ぐ
- **最後の管理者を `member` にできない。** 上の条件だけでは、管理者が2人いて互いを降格させると0人になれる
- `demo` は選択肢に出さない（`users.role` に確保済みだがUIには出さない既存方針）
- メールの重複は既存の `uniqueness: { case_sensitive: false }` が拒否する（`user.rb:34`）

**卒業生かどうかは年度からの計算結果です**（`user.rb:63`）。切り替えるボタンは作らず、年度を直せば現役／卒業生の表示も直ります。

### 3.4 氏名（項目6）

**オーナー決定（2026-09-12）: 本人と管理者の両方が変えられるようにします。**

| 経路 | 誰が | 何のために |
|---|---|---|
| `PATCH /api/users/me` に `name` を足す | 本人 | 改姓 |
| `PATCH /api/admin/users/:id` に `name` を足す | 管理者 | 発行時の打ち間違い |

同じことをする入口が2つになりますが、**直したい人が違います。** 改姓は本人が気づき、
打ち間違いは発行した管理者が気づきます。片方だけにすると、もう片方が必ず人に頼むことになります。

> この決定は `docs/spec-my-page.md:286` の「管理者が氏名・学科を直す UI は作らない」
> （2026-09-10）を覆します。**学科は据え置き**で、本人だけが編集できる状態のままです。

**`spec-v2.2.md` §4.1 の「名前を変えられると他人になりすませる」は残ります。**
氏名の変更は参加者一覧にも主催欄にも即座に効きます。承認や履歴は持ちません
（操作ログは対象外。§5）。部内向けで、アカウントは管理者が手で発行する運用を前提にした判断です。

### 3.5 タグ管理（項目7）

**この項目は `docs/spec-tags.md` に置き換わりました。** そちらを読んでください。

この文書を書いた時点では「管理者が `/admin/tags` でタグを作る」前提でしたが、
その後の判断で**タグは自由記述**になりました。作る場所は各フォームに移り、
`/admin/tags` は「直す場所」（一覧・改名・使用0件の削除）になります。

### 3.6 プロジェクトの脱退（項目8）

**オーナー決定（2026-09-12）: 論理削除で、かつ申請制にします。**（提案時の案ロ＋申請）

プロジェクトは継続的に成果物を作る活動で、抜けられると owner が引き継ぎを考える必要が
あります。黙って消えると気づけないので、イベントの参加キャンセルと同じ
「1クリックで抜ける」にはしません。

**列を2本足します**（`spec-v2.2.md` §2.6 に反映済み）。

| 列 | 意味 |
|---|---|
| `withdrawal_requested_at` | 脱退を申請した時刻（null = 申請していない） |
| `cancelled_at` | 脱退が承認されて抜けた時刻（null = 参加中） |

ユニークインデックスを `WHERE cancelled_at IS NULL` の部分ユニークに貼り替えます。
イベント側と同じ形になり、抜けたあと参加し直せます。

**エンドポイントは `docs/api-spec.md` の「プロジェクトの脱退」を参照してください。**

**`status`（0:approved / 1:pending / 2:rejected）は使いません。** あちらは「参加を承認するか」
の軸で 🟡 MVPは0固定です。脱退は別の軸なので、1つの列に2つの意味を持たせません。

**owner 自身は脱退できません。** 抜けると持ち主のいない企画が残ります。owner の付け替えは
MVP 対象外（co_organizer と同じ）。

注目スコアはイベント専用（§3）でプロジェクトの参加履歴を使わないため、計算に影響はありません。

> **`CLAUDE.md` §10 の「プロジェクト脱退申請」を外す必要があります。** §11-6 により
> 人間が変える決まりなので、別のPRで渡します。

## 5. スコープ外

- **メール送信によるパスワードリセット** — 通知機能を作らない方針（`CLAUDE.md` §10）
- **パスワード変更時に他端末のセッションを切ること** — `session_token` 列が要る（3.1 の⚠️）
- **企画の owner の付け替え** — co_organizer と同じくMVP対象外
- **操作ログ・監査証跡** — 誰がいつ権限を変えたかの記録。統計ダッシュボードと同じく対象外
- **`demo` ロールのUI**

## 7. 受け入れ条件

1. 各操作が `rails console` を開かずに完了できる
2. 画面に残っている「`rails console` で対応します」の注記が、実装した範囲について消えている
3. **認可はすべてサーバー側で判定している**（`CLAUDE.md` §3-2）。`curl` で直接叩いても、権限の無い操作が 403 / 422 で止まる
4. 新しいロジックに対応する spec がある（`CLAUDE.md` §11-4）。特に「最後の管理者を降格できない」の境界
5. `bundle exec rspec` / `bundle exec rubocop` / `npm run lint` / `npm run typecheck` が通る
