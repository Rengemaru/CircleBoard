## 1. 何が問題か

いま `users` が持っているのは、**アカウントを成立させるための情報だけ**です。

```
name / email / password_digest / role / enrollment_year / graduation_year / suspended_at
```

このうち画面に出るのは**名前だけ**です。企画の一覧にも参加者一覧にも名前しか出ないので、次のことが起きます。

- 参加者一覧に名前が並んでも、**その人が何をやっている人なのか分からない**
- 「Webアプリ開発チーム」に入りたい人がいても、**自分が何をできるかを置いておく場所がない**
- サークルの活動と、**就活で見せられる素材（作ったもの・使える技術）が繋がらない**

`CLAUDE.md` §0 は「サークルでの実運用とポートフォリオ映えが衝突したら実運用を優先する」としていますが、**今回は衝突しません。** 部内で「誰が何をできるか」が分かることは、企画を組むときの実利です。

## 2. 何を書けるようにするか

`users` に3列、新しいテーブルを2つ足します。

### 2.1 users への追加列

| カラム | 型 | 制約 | 備考 |
|---|---|---|---|
| `department` | string | NULL可 | 学科。自由入力。50字まで |
| `bio` | text | NULL可 | 自己紹介。500字まで |

**学科を選択肢にしないのは、学科名が大学ごとに違い、改組でも変わるためです。** 選択肢を持つと、変わるたびにマイグレーションが要ります（`CLAUDE.md` §4 が PostgreSQL の ENUM 型を避けているのと同じ理由）。

**`bio` を `text` にしたのは、改行を含む数百字を想定しているためです。** `string`（varchar 255）だと足りません。

### 2.2 user_tags（スキル）

**既存の `tags` テーブルを再利用します。** 企画に付けるタグ（Web開発 / ゲーム制作 / 機械学習 / …）が、そのまま「使える技術」として使えます。

| カラム | 型 | 制約 |
|---|---|---|
| `user_id` | bigint | FK users, NOT NULL, ON DELETE CASCADE |
| `tag_id` | bigint | FK tags, NOT NULL, ON DELETE CASCADE |

- `(user_id, tag_id)` に複合ユニークインデックス
- 1人あたりの上限は**5件**。アプリ側で検証する

**新しいタグ用のテーブルを作らない理由**は、`/events` や `/projects` の絞り込みと同じ語彙になるからです。「機械学習ができる人」と「機械学習の企画」が別の言葉で管理されると、探すときに繋がりません。

**タグの新規作成UIは作りません**（`docs/api-spec.md` §4 のとおり、タグ作成APIは無い）。管理者が `rails console` で足す運用のままです。

### 2.3 user_links（外部リンク）

| カラム | 型 | 制約 |
|---|---|---|
| `user_id` | bigint | FK users, NOT NULL, ON DELETE CASCADE |
| `label` | string | NOT NULL。20字まで |
| `url` | string | NOT NULL。`http://` または `https://` で始まること |
| `position` | integer | NOT NULL, default: 0。並び順 |

- 1人あたりの上限は**3件**
- `(user_id, position)` にインデックス

**`github_url` / `x_url` のような固定列にしない理由**は、学生が置きたい先が人によって違うためです（GitHub・X・Zenn・Qiita・個人サイト・作品のURL）。固定列にすると、増やすたびにマイグレーションが要ります。

**`label` を自由入力にするのは、上と同じ理由です。** ただし表示は必ずラベルの文字列で、**URL をそのまま画面に出しません**（後述のセキュリティ）。

## 3. 誰に見せるか

**ログインした人だけ。** 未ログインには一切返しません。

| リソース | 未ログイン | ログイン済み | 本人 | 管理者 | サイネージ |
|---|---|---|---|---|---|
| プロフィール（学科・自己紹介・スキル・リンク） | ❌ | ✅ 閲覧 | ✅ 閲覧・編集 | ✅ 閲覧 | ❌ |

`spec-v2.2.md` §4.1 の表にこの行を足します。**§4.1 は確定済みの節なので、この仕様の承認をもって変更とします。**

### 実装上の原則（§3-2）

**シリアライザでキーごと落とします。** フロントの条件レンダリングで隠すのは禁止です。`curl` で叩けば見えてしまうため。

```ruby
# 未ログインなら profile キーそのものを返さない
return base unless signed_in?
base.merge(profile: { department:, bio:, tags:, links: })
```

**管理者だけが見える情報は増やしません。** 管理者も「ログインした人」として同じものを見ます。

## 4. 画面

### 4.1 `/me`（自分のマイページ）

ログイン必須。未ログインなら `LoginRequired`（既存）。

```
アカウント        名前 / メールアドレス / 入学・卒業年度 / 権限
                  （編集はできない。変更は管理者に依頼する）

プロフィール      学科 / 自己紹介 / スキル / リンク        [編集する]

自分の企画        owner になっている企画の一覧
参加中の企画      参加表明しているイベント・プロジェクト
```

**「自分の企画」「参加中の企画」は既存のデータだけで出せます。** 列の追加は要りません。マイページを開いたときに一番見たいのは「自分が今なにに関わっているか」なので、プロフィールと同じ画面に置きます。

### 4.2 `/me/edit`（編集）

`FormControl` + `Input` / `Textarea`（Phase 8 で揃えたもの）を使います。

- 学科: `Input`
- 自己紹介: `Textarea`（残り文字数を出す）
- スキル: 既存タグから選ぶ。`/create` のタグ選択と同じ `FilterChip`
- リンク: ラベルとURLの組を最大3行。行の追加・削除

**保存後は `/me` に戻り、「保存しました」を出します**（Issue #43 で決めた「何が起きたかを文言で伝える」）。

### 4.3 `/users/:id`（他の人のプロフィール）

ログイン必須。**編集はできません。** 出すのは名前・学科・自己紹介・スキル・リンクと、その人が owner の企画だけです。

**参加中の企画は出しません。** 自分の画面には出すが他人の画面には出さない、という差を付けるのは、「誰がどこに参加しているか」を一覧できると、部内であっても居心地の悪さが出るためです。

### 4.4 導線

| どこから | どこへ |
|---|---|
| ヘッダーの利用者名 | `/me`（いまはただの文字列） |
| イベント詳細の参加者チップ | `/users/:id` |
| 企画の「主催」欄の名前 | `/users/:id` |

## 5. API

`docs/api-spec.md` に追記します。**キーは `snake_case`**（`CLAUDE.md` §4）。

| メソッド | パス | 認証 | 返すもの |
|---|---|---|---|
| GET | `/api/users/me` | ログイン必須 | 自分のアカウント＋プロフィール |
| PATCH | `/api/users/me` | ログイン必須 | 更新後のプロフィール |
| GET | `/api/users/:id` | ログイン必須 | 名前＋プロフィール（本人以外はメールを返さない） |

### 返す形

```json
{
  "id": 2,
  "name": "山田太郎",
  "department": "情報工学科",
  "bio": "Webアプリを作っています。\nReact と Rails を触っています。",
  "enrollment_year": 2026,
  "graduation_year": 2030,
  "tags": [{ "id": 1, "name": "Web開発" }],
  "links": [{ "id": 1, "label": "GitHub", "url": "https://github.com/xxx" }]
}
```

- **`email` は本人にだけ返します。** 他人のメールアドレスを配る理由がありません
- `role` と `suspended_at` は返しません。**管理画面の情報であって、プロフィールではありません**

### PATCH で受け取るもの

```json
{
  "department": "情報工学科",
  "bio": "…",
  "tag_ids": [1, 4],
  "links": [{ "label": "GitHub", "url": "https://github.com/xxx" }]
}
```

- **`name` / `email` / `role` / 年度は受け付けません。** 受け付けると、名前を変えて他人になりすませます。変更は管理者の仕事です（Issue #4）
- `links` は**丸ごと置き換え**ます。行の追加・削除・並べ替えを個別のAPIにすると、画面の操作と1対1にならず往復が増えます

## 6. 検証とセキュリティ

### 6.1 入力の検証（モデル）

| 項目 | 制約 | 破ったとき |
|---|---|---|
| `department` | 50字まで | 422 |
| `bio` | 500字まで | 422 |
| スキル | 5件まで。存在するタグのIDのみ | 422 |
| リンク | 3件まで。`label` 20字まで | 422 |
| リンクの `url` | `http://` または `https://` で始まること | 422 |

**URL のスキームを検証するのは、`javascript:` を弾くためです。** 利用者が入れた文字列をそのまま `<a href>` に置くと、**他の部員がクリックしたときにスクリプトが動きます**。フロント側でも弾きますが、**サーバー側の検証を正とします**（フロントだけの検証は `curl` で回避できる）。

### 6.2 表示

- 外部リンクは `target="_blank"` + `rel="noreferrer noopener"`。**`noopener` が無いと、開いた先から元のタブを操作できます**
- `bio` の改行は `whitespace-pre-wrap` で出します。**HTML としては解釈しません**（React が既定でエスケープする）

### 6.3 認可

- `PATCH /api/users/me` は**必ず `current_user` を更新対象にします。** リクエストの `id` を信用しません（`docs/api-spec.md` §2 で `owner_id` について決めたのと同じ）
- 停止中（`suspended_at` あり）の利用者は、セッションが無効になるので自動的に弾かれます（Issue #72 で確認済み）

## 9. やらないこと

- **画像アップロード**（§1 で Active Storage を採用していない）
- **公開設定**（項目ごとの公開/非公開）
- **他人のプロフィールの管理者による編集** — Issue #4 の範囲です。`department` 列はこの仕様で追加するので、Issue #4 は「一覧に学科を出す」「管理者が氏名・学科を直す」だけに縮みます
- **プロフィールの検索・一覧**（「機械学習ができる人を探す」）— 欲しくなるのは分かりますが、まず書ける場所を作ってからにします
- **自己紹介の Markdown 対応** — 記法を覚える負担と、レンダリングの安全性の両方が乗ります
