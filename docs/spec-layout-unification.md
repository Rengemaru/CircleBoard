# 仕様: 管理画面と通常画面のレイアウト統合

オーナー指示（2026-09-10）に基づく仕様書です。**実装前にこの文書の承認を得ます。**

- 管理画面と通常画面を統合する。分かれている意味が現状ない
- 管理画面の左にあるナビゲーションをヘッダーに移す。左にある理由がない
- 配置と余白は SmartHR Design System のパターンに合わせる

---

## 1. 現状

シェル（画面の外枠）が2つあります。

| | member 側 | admin 側 |
|---|---|---|
| 外枠 | `components/MemberPage.tsx` | `pages/admin/AdminLayout.tsx` |
| ヘッダー | `SiteHeader`（上部・横並び） | `AdminSidebar`（左200px固定・縦並び） |
| 本文の幅 | `max-w-3xl`（768px） | 残り全部（可変） |
| 本文の余白 | `px-6 py-6` | `p-6` |
| 背景 | 既定 | `bg-gray-50` |
| 画面名 | `PageHeading` | `PageHeading`（トップバーの中） |

同じことを2箇所で決めているため、次の重複が起きています。

- **ロゴが2箇所**（`SiteHeader` の「CircleBoard」と `AdminSidebar` の「CircleBoard」）
- **利用者名が2箇所**（ヘッダー右端とサイドバー上部）
- **画面を移る導線が2箇所**（`SiteHeader` の「管理」ボタンと `AdminSidebar` の「通常画面に戻る」）
- **余白の基準が2組**（`px-6 py-6` と `p-6`、本文幅 768px と可変）

「管理」ボタンと「通常画面に戻る」は、**2つのシェルを行き来するためだけに存在します。** シェルが1つになれば両方要りません。

### 分かれている必然性が無いこと

SmartHR の「権限による表示制御」パターンは、**権限が無い機能は操作 UI ごと非表示にする**（パターンA: 非表示・理由なし、例として「管理者権限のない機能」）としています。**画面の領域を分けることは求めていません。**

CircleBoard の管理機能は5画面で、対象も同じデータ（企画・アカウント・サイネージ）です。領域を分けるほどの規模と独立性がありません。

---

## 2. 変えること / 変えないこと

### 変えること（UI のみ）

- シェルを1つにする
- 管理画面のナビゲーションをヘッダーへ移す
- 余白・本文幅の基準を1組にする

### 変えないこと

- **URL**（`/admin/*` のまま）。ブックマークが壊れ、リダイレクトを足す必要が出るため
- **API と認可**。`CLAUDE.md` §3-2 のとおり、管理 API はサーバー側で `role` を検証し続けます。**ナビゲーションから項目を隠すのは表示の話であって制限ではありません**
- **画面の中身**（各画面の見出し・表・フォーム）。この仕様は外枠だけを対象にします
- **サイネージ（`/signage`）**。ナビゲーションを一切表示しない仕様なので対象外です

## 3. 目標のレイアウト

SmartHR のページレイアウトパターンのうち、**「サイドナビゲーションとコンテンツの2カラム」をやめて「コレクション（テーブル）」「シングル（1カラム）」に寄せます。**

パターン集は、2カラムのサイドナビゲーションを「設定画面など、ナビゲーション項目が多い・階層構造がある場合」に使うとしています。CircleBoard の管理機能は5項目・階層なしなので該当しません。また**「モバイルでは AppNavi に操作を集約し、このレイアウトは避けてください」**とも書かれています。

```
┌─────────────────────────────────────────────┐
│ CircleBoard                部長 管理  ログアウト │ ← 上段（自前の SiteHeader）
├─────────────────────────────────────────────┤
│ ホーム  イベント  プロジェクト  管理 ▾           │ ← 下段（smarthr-ui の AppNavi）
└─────────────────────────────────────────────┘
      ┌───────────────────────────────┐
      │ 画面名（PageHeading）           │ ← Container の中
      │                               │
      │ 本文（Base / Table / Form）     │
      └───────────────────────────────┘
```

### 上段と下段を分ける理由

smarthr-ui の `AppHeader` は `Header` と `AppNavi` を結合したものですが、**SmartHR プロダクト専用の概念（テナント、アプリ切替、リリースノート、ヘルプページ）を前提にしています。** CircleBoard には無いものばかりなので `AppHeader` は使いません。

`Header` 単体も「独自のヘッダー構成が必要なときのみ」とされており、こちらもアカウント設定など SmartHR 共通機能を持ちます。

**上段は自前の `SiteHeader` を維持し、下段のナビゲーションだけ `AppNavi` に置き換えます。** ロゴと SmartHR Blue は使用不可（`instructions.md` Phase 8 の調査済み事項）なので、配色は今までどおり自前で決めます。

## 4. ナビゲーションの設計

### 項目

| 表示 | 遷移先 | 誰に見せるか |
|---|---|---|
| ホーム | `/` | 全員 |
| イベント | `/events` | 全員 |
| プロジェクト | `/projects` | 全員 |
| **管理 ▾** | ドロップダウン | **`role === "admin"` のときだけ** |
| └ ダッシュボード | `/admin` | 同上 |
| └ ユーザー管理 | `/admin/users` | 同上 |
| └ 企画一覧（全件） | `/admin/posts` | 同上 |
| └ ピン留め設定 | `/admin/pin` | 同上 |
| └ サイネージトークン | `/admin/signage` | 同上 |

### 管理をドロップダウンにまとめる理由

平らに並べると **8項目**になります。ナビゲーションは「アプリケーション内の主要機能を切り替える」ためのもので、日常的に使う3つ（ホーム・イベント・プロジェクト）と、部長だけが時々使う5つを同じ重みで並べると、主要機能が埋もれます。

`AppNaviDropdownMenuButton` でまとめれば、**全員に見えるのは4項目**（うち1つは管理者にしか出ない）に収まります。

現行のサイドバーが付けていたグループ見出し（メイン / 管理 / サイネージ / アカウント）は落とします。5項目にグループ見出しが4つあり、分類が項目数に見合っていませんでした。

### 権限による出し分け

`role !== "admin"` の人には「管理」自体を出しません（パターンA: 非表示・理由なし）。**これは表示の話です。** 管理 API はサーバー側で必ず 403 を返し、直接 URL を叩いた場合の画面側の案内（「管理者だけが使える画面です」）も残します。

### 現在地の表示

`AppNaviCustomTag`（`tag` に react-router の `Link`）＋ `current` を使います。`/admin/users/new` のような配下の画面でも「管理」を選択状態にします。現行の `NavItem` が持っている「前方一致で親を選択状態にする」挙動を引き継ぎます。

## 5. 余白と幅の基準

SmartHR の「余白とレイアウト」に合わせます（**16px を `1` とするトークン**）。

| 場所 | 値 | 使うもの |
|---|---|---|
| 本文領域のパディング | `2`（32px）／モバイルは上下 `1.5`・左右 `1` | `Container`（既定値がこれ） |
| セクション間 | `2`（32px） | `Stack gap={2}` |
| セクション内の要素間 | `1.5`（24px） | `Stack gap={1.5}` |
| 見出しとコンテンツの間 | `1`（16px） | `Stack gap={1}` |
| 小要素の横並び（アイコン・ラベル） | `0.5`（8px）または `0.25`（4px） | `Cluster gap="XS"` / `"XXS"` |

**`Container` を導入します。** 現在は `MemberPage` が `mx-auto px-6 py-6 max-w-3xl` を直接書いており、余白（24px）が SmartHR の基準（32px）とずれています。

### 本文の幅

1つに固定せず、**画面の中身に応じて `Container` の `size` を選びます。**

| size | 使う画面 | 理由 |
|---|---|---|
| `NARROW` | `/login`、`/create` | フォーム1枚。入力欄が画面幅いっぱいに伸びると読む場所が分からなくなる（現行 `width="narrow"` と同じ考え） |
| `DEFAULT` | `/`、`/events`、`/events/:id`、`/projects`、`/projects/:id`、`/legal`、`/admin`、`/admin/pin`、`/admin/signage`、`/admin/users/new`、404 | 読む画面 |
| `WIDE` | `/admin/users`、`/admin/posts` | 列の多い表。現行は幅の制限が無く、統合して 768px にすると横スクロールが常態化する |

**表の画面だけ広くするのは、SmartHR のパターンが中身ごとにレイアウトを分けているのと同じ考え方です。** 「コレクション（テーブル）」と「シングル（1カラム）」は別のパターンとして定義されています。

## 6. 画面ごとの影響

| 画面 | 変わること |
|---|---|
| `/`、`/events`、`/events/:id`、`/projects`、`/projects/:id`、`/create`、`/login`、`/legal`、404 | ヘッダーにナビゲーションの段が増える。本文の余白が 24px → 32px。管理者にだけ「管理 ▾」が出る |
| `/admin`、`/admin/users`、`/admin/users/new`、`/admin/posts`、`/admin/pin`、`/admin/signage` | 左のサイドバーが消え、上のヘッダーから移動する。**画面の中身は変えない** |
| `/signage` | 変更なし |

### 消えるもの

- `AdminSidebar`（`AdminLayout.tsx` 内）とその `NavGroup` / `NavItem`
- 「ADMIN」バッジ — シェルが1つになると「いま管理モードにいる」という状態自体が無くなるため
- 「通常画面に戻る」 — 戻る先が同じ画面になるため
- `SiteHeader` の「管理」ボタン — ナビゲーションの「管理 ▾」に統合されるため

### 残すもの

`AdminLayout` が持っている**未ログイン／管理者以外／セッション確認失敗の3分岐**（Issue #72、PR #114）は、そのまま統合後のシェルの中に残します。名前を `AdminOnly` に変え、`children(user: CurrentUser)` の形（検証済みの管理者を渡す）も維持します。

## 7. 実装の分割

`CLAUDE.md` §11-1（1 PR あたり非テスト300行まで）に従い、**どの時点で止めても main が壊れない順**にします。

| 順 | 内容 | 見込み |
|---|---|---|
| L-1 | `SiteHeader` のナビゲーションを `AppNavi` に置き換える。項目は今までの3つのまま。**管理画面には手を付けない** | 60行 |
| L-2 | `MemberPage` に `Container` を入れ、余白と幅の基準を SmartHR に合わせる。`width="narrow"` を `size` に置き換える | 60行 |
| L-3 | `AppNavi` に「管理 ▾」を足す（`role === "admin"` のときだけ）。この時点では `SiteHeader` の「管理」ボタンと重複するが、どちらからでも行ける | 60行 |
| L-4 | `AdminLayout` を `AdminOnly` に置き換え、統合後のシェルを使うようにする。サイドバー・ADMIN バッジ・「通常画面に戻る」・「管理」ボタンを削除。表の2画面に `WIDE` を指定 | 150行 |
| L-5 | 余白・見出しの通し確認と、崩れの手直し | 状況次第 |

L-1 〜 L-3 は管理画面に影響しません。L-4 で初めて見た目が大きく変わります。

## 8. 確認する項目

各 PR で、ブラウザで次を実測します（数値はこのセッションでの計測と同じ方法）。

1. **全15ルートが白画面にならない**
2. **管理者以外に「管理 ▾」が出ない**（`role` を `member` にしたセッションで確認。API は 403 のまま）
3. **現在地の表示**が正しい（`/admin/users/new` で「管理」が選択状態）
4. **表の画面で、ページ全体が横スクロールしない**（表の中だけがスクロールする）
5. **見出し構造**（`h1` → `h2` → `h3`）が変わっていない
6. **タブのタイトル**が画面ごとに出る（PR #135・#137 で直した挙動を壊さない）
7. **キーボードだけで**ナビゲーションのドロップダウンを開閉できる

## 9. 決めてほしいこと

### (1) 管理機能の出し方

- **A（推奨）**: 「管理 ▾」のドロップダウンにまとめる。全員に見えるのは4項目
- B: 8項目を平らに並べる。1回のクリックで各画面へ行けるが、主要機能が埋もれる

### (2) 表の画面の幅

- **A（推奨）**: `/admin/users` と `/admin/posts` だけ `WIDE`。他は `DEFAULT`
- B: 全画面 `DEFAULT` に揃える。表は横スクロールに任せる

### (3) URL

- **A（推奨）**: `/admin/*` のまま
- B: `/users` `/posts` などに移す。統合の徹底にはなるが、`/projects` などと名前が競合し、リダイレクトも要る

---

## 10. この仕様でやらないこと

- 管理機能の追加・削除（画面の数は5つのまま）
- 権限の設計変更（`role` は `admin` / `member` / `demo` のまま）
- モバイル専用のナビゲーション（`CLAUDE.md` §10 で対象外）
- サイネージへの適用
